# 云同步修复与云端部署计划

## 概述

当前计算机二级学习网页的云同步功能中，方案2（云端同步码）使用的 npoint.io API 返回 500 错误，导致方案2和依赖它的方案3（二维码同步）均不可用。本计划将 npoint.io 替换为经过实测验证的 jsonblob.com API，并将整个网站部署到 BytePlus Edge Pages 云端平台，实现手机跨设备访问。

## 当前状态分析

### 已正常工作的部分
- 方案1（导出/导入JSON文件）：完全可用
- 方案4（Firebase自动同步）：代码完整，需用户自行配置Firebase项目
- 本地HTTP服务器已运行，网站各功能模块（章节学习、练习题、错题本、模拟测试、速记卡、收藏夹）均正常

### 需要修复的问题
- **方案2 云端同步码**：npoint.io POST `https://api.npoint.io/` 返回 500 错误
- **方案3 二维码同步**：依赖方案2的 `uploadToCloud()`，因此也不可用
- **云端部署**：网站仅在本地 localhost 运行，手机无法访问

### 影响范围
所有 npoint 引用仅集中在2个文件：
- `assets/js/sync.js`：uploadToCloud()、downloadFromCloud()、getCloudSyncInfo()
- `assets/js/views/settings.js`：方案2的描述文字和UI渲染

## jsonblob.com API 实测验证结果

经实际网络请求验证（POST/GET/PUT 全流程），确认以下技术事实：

### API 端点

| 功能 | 方法 | URL | 成功状态 |
|------|------|-----|----------|
| 创建新 blob | POST | `https://api.jsonblob.com` | 201 |
| 读取 blob | GET | `https://api.jsonblob.com/{blobId}` | 200 |
| 更新 blob | PUT | `https://api.jsonblob.com/{blobId}` | 200 |

### 关键差异（与 npoint.io 对比）

1. **blobId 在响应头中，不在响应体中**：npoint.io 在响应体返回 `{id: "..."}`；jsonblob.com 响应体只回显原始数据，blobId 仅在响应头 `X-jsonblob-id` 或 `Location` 中
2. **匿名 blob 有 24 小时过期限制**：响应头 `X-jsonblob-expires-at` 标明过期时间，且 PUT 更新不刷新 TTL
3. **CORS 完全支持**：`Access-Control-Expose-Headers` 包含 `Location` 和 `X-jsonblob-id`，浏览器可正常读取
4. **限流**：匿名用户 6 次写入/60 秒，60 次读取/60 秒

### blobId 提取方式
- 首选：`response.headers.get('X-jsonblob-id')` → 直接得到 UUID
- 备选：`response.headers.get('Location')` → 返回 `/{blobId}`，需去掉前导斜杠

## 实施步骤

### 第一部分：修复云同步（sync.js）

#### 步骤1：更新文件头注释
- 第4行：`JSONBin云端同步（同步码）` → `jsonblob云端同步（同步码，24小时有效期）`
- 第87行：`npoint云端同步（免注册，同步码）` → `jsonblob云端同步（免注册，同步码，24小时有效期）`

#### 步骤2：重写 `uploadToCloud()` 方法
- 将 POST `https://api.npoint.io/` 改为 POST `https://api.jsonblob.com`
- 从响应头 `X-jsonblob-id` 提取 blobId（备选 `Location` 头）
- 保存过期时间到 `Store.set('cloud_sync_expires', expiresAt)`
- 增加 429 限流检测和友好提示
- 成功后通知显示完整同步码

#### 步骤3：重写 `downloadFromCloud(syncId)` 方法
- 将 GET `https://api.npoint.io/{id}` 改为 GET `https://api.jsonblob.com/{syncId}`
- 增加 404 过期处理：提示"同步码无效或数据已过期（有效期24小时）"
- 增加 429 限流处理
- 同步保存过期时间

#### 步骤4：新增 `updateToCloud()` 方法
- 用 PUT `https://api.jsonblob.com/{blobId}` 更新已有 blob 数据
- 同步码不变，TTL 不变
- 当 PUT 返回 404（已过期）时，自动回退调用 `uploadToCloud()` 重新创建
- 通知用户"原同步码已过期，已生成新同步码"

#### 步骤5：扩展 `getCloudSyncInfo()` 方法
- 增加 `expires` 字段：返回过期时间
- 增加 `expired` 字段：判断是否已过期（与当前时间比较）

#### 步骤6：方案3（二维码同步）无需改动
- `generateQRCode()` 和 `autoSyncFromURL()` 依赖 `uploadToCloud()`/`downloadFromCloud()`，自动受益于新实现

### 第二部分：更新设置页UI（settings.js）

#### 步骤1：更新方案2描述文字
- 将"使用npoint.io免费服务"改为"使用 jsonblob.com 免费服务，无需注册。同步码有效期为24小时，过期后需重新上传获取新码。"

#### 步骤2：改造方案2卡片主体

- 未过期时显示"更新云端数据"按钮（调用 `updateToCloud()`）

#### 步骤3：新增 `SettingsView.updateToCloud()` 方法

## 假设与决策

1. **选择 jsonblob.com 而非其他服务**：实测验证 CORS 完整、API 简洁、免注册免费用，适合本场景
2. **24小时过期限制的应对**：UI 展示有效期 + 过期自动回退重新上传；长期多设备同步引导用户使用方案4（Firebase）
3. **PUT 不刷新 TTL 的处理**：更新成功提示中明确"有效期不变"；过期后自动 POST 新码
4. **部署平台选择 BytePlus**：技能已加载，支持一键部署静态站点，CDN 加速
5. **不修改 Firebase 方案**：代码已完整，用户自行配置即可
6. **不新增 CSS**：复用现有 `.badge-hard`、`.sync-code-display`、`.sync-code-hint` 等样式类
